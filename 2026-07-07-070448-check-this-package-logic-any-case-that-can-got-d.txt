● Verdict — Duplicate sends with your config

  Yes, your config WILL send duplicate Discord messages.

  You use CurlBehavior.chronological + webhookInspectors: [discordInspector]
  with CurlInterceptorVersion.auto. The factory routes to V2 (any webhook
  inspector → V2, see curl_interceptor_factory.dart:149-152), and V2 has a
  double-dispatch bug.

  Why duplicates happen

  The same HTTP response fires onResponse in CurlInterceptorV2
  (curl_interceptor_v2.dart:157). Inside, two unrelated call paths each iterate
  webhookInspectors and call sendCurlLog(...):

  Step: 1
  Line: curl_interceptor_v2.dart:164 → curl_utils.dart:297-310
  What it does: Direct call from inside CurlUtils._handleOn
  Dedupe?: None
  ────────────────────────────────────────
  Step: 2
  Line: curl_interceptor_v2.dart:182 → :_queueWebhookNotifications
  What it does: Fire-and-forget through WebhookCache + CircuitBreaker + Retry
  Dedupe?: Cached for 1 min via WebhookCache, but the first call has already
  left
     the building

  Same shape for onError (v2.dart:208 + :226) and a weaker duplicate at
  onRequest (:124 + :138, the latter is suppressed for status -1 by isMatch
  unless ResponseStatus.unknown is enabled).

  Net effect per successful request: 2 Discord posts (one raw, one
  cached-throttled next-time). Per error: 2 posts.

  What does NOT cause duplicates

  - CurlBehavior.chronological itself (only controls whether cURL re-prints in
  the response block).
  - printer: logger.info (a separate terminal stream, not a second webhook).
  - V1 ↔ V2 dual install under version: auto (only one is created).

  Recommended immediate workaround

  Force V1, which dispatches each event exactly once:

  return CurlInterceptorFactory.create(
    ...
    version: CurlInterceptorVersion.v1,   // single-dispatch
  );

  If you need V2 features, drop webhookInspectors from the factory and add a
  side-channel listener. Or shorten/eliminate WebhookCache mismatch by routing
  all sends through _sendWebhookNotification only.

  ---
  Critical bugs

  1. Double webhook dispatch (shown above) —
  lib/src/interceptors/curl_interceptor_v2.dart:124+138, :164+182, :208+226.
  Highest priority — observable on every request.
  2. requestHeaders: false does not redact webhook payloads —
  CurlHelper.generateCurlFromRequestOptions always bakes Authorization/Cookie
  headers into the cURL string. _handleOn then forwards that cURL verbatim to
  inspector.sendCurlLog at curl_utils.dart:300-307. Your config sets
  requestHeaders: false, but Discord will still receive those headers. Fix:
  redact headers in the cURL string before webhook send, separately from console
  display.
  3. Response time always N/A in webhooks — v2.dart:158 removes the stopwatch
  from _stopwatches, then _sendWebhookNotification (:319) reads it. Always null
  → always N/A.
  4. Webhook fires for in-flight requests with bogus status — onRequest queues a
  notification with statusCode = -1. If ResponseStatus.unknown is enabled in
  defaultInspectionStatus, every request pings Discord on send. Not your config
  today, but a foot-gun.
  5. Telegram _getWebhookUrl uses botToken.substring(0, 10) as cache key — many
  Telegram bot tokens share prefixes, so two inspectors will collide on
  WebhookCache + CircuitBreaker.

  Code smells worth noting

  - WebhookCache _lastSent grows unbounded — no eviction; long-running services
  leak memory (lib/src/patterns/webhook_cache.dart).
  - Telegram sender adds a CurlInterceptor to its inner Dio — outbound
  Discord/Telegram payload (including bot tokens, chat contents) gets cached to
  disk if cache is enabled (lib/src/inspector/telegram_inspector.dart).
  - Factory has parameter explosion + 3 near-duplicate constructors (create,
  createV1, createV2, withFilters). Consider one CurlInterceptorConfig value
  object.
  - webhookInspectors is a mutable List consumed without snapshotting in
  _sendWebhookNotification — caller mutation mid-flight =
  ConcurrentModificationError.
  - printer default fallback — uses kPrinter = log from somewhere that does not
  match the void Function(String) typedef. Anything instantiating CurlOptions()
  without overriding printer is at risk in strict builds.
  - V1 and V2 duplicate ~80% of the surface without inheritance — bug fixes must
  land twice.
  - Inconsistent error handling — HiveCacheRepositoryImpl.init swallows,
  _sendWebhookNotification swallows (via developer.log), but
  WebhookSenderBase.sendToAll returns bools. Callers can't tell if a send
  actually happened.
  - _isComplexConfiguration auto-forces V2 even with no webhooks when
  prettyConfig.blockEnabled: true (the default), defeating the "V1 fallback"
  promise.
  - No tests exist for the duplicate-dispatch path.
  test/discord_inspect_test.dart only verifies mockDio.post is called once for a
  single send(message); integration tests never assert "one Discord post per
  HTTP request".

  Bottom line

  Your config + version: auto will spam Discord with two posts per HTTP response
  (two per error). Pin version: CurlInterceptorVersion.v1 for now if you need a
  one-line fix, or open an upstream bug on V2's split dispatch in
  curl_interceptor_v2.dart.

  Layer 1 — DioCurlInterceptor (lib/src/dio_curl_interceptor.dart)

  class DioCurlInterceptor extends Interceptor {
    final CurlRelay _relay;
    final CurlConfig _config;

    DioCurlInterceptor({required CurlConfig config, CurlRelay? relay})
      : _config = config,
        _relay = relay ?? CurlRelay.fromConfig(config);

    @override
    void onRequest(RequestOptions opts, RequestInterceptorHandler h) {
      _safe(() {
        final event = CurlEvent.fromRequest(opts);
        _stopwatches[event.id] = Stopwatch()..start();
        _relay.dispatch(event);  // fire-and-forget
      });
      return h.next(opts);
    }

    @override
    void onResponse(Response resp, ResponseInterceptorHandler h) {
      _safe(() {
        _stopwatches.remove(resp.requestOptions)?.stop();
        final event = CurlEvent.fromResponse(resp,
  _stopwatches[resp.requestOptions]);
        _relay.dispatch(event);
      });
      return h.next(resp);
    }

    @override
    void onError(DioException err, ErrorInterceptorHandler h) {
      _safe(() {
        _stopwatches.remove(err.requestOptions)?.stop();
        final event = CurlEvent.fromError(err);
        _relay.dispatch(event);
      });
      return h.next(err);
    }

    void dispose() => _relay.dispose();
  }

  Layer 2 — CurlRelay (lib/src/relay/curl_relay.dart)

  class CurlRelay {
    final List<CurlSink> _sinks;
    final DedupeCache _dedupe;
    final RetryPolicy _retry;
    final Map<String, CircuitBreaker> _breakers;
    final Timer? _cleanupTimer;

    Future<void> dispatch(CurlEvent event) async {
      // 1. dedupe — chặn duplicate trong cooldown window
      if (!_dedupe.shouldDispatch(event)) return;

      // 2. fire-and-forget — không block request
      unawaited(_handle(event));
    }

    Future<void> _handle(CurlEvent event) async {
      for (final sink in _sinks) {
        final key = sink.id;
        final breaker = _breakers.putIfAbsent(key, () => CircuitBreaker(...));

        try {
          await breaker.call(() => _retry.execute(
            () => sink.handle(event),
            operationName: 'sink:${sink.name}',
          ));
        } catch (_) {
          // relay không raise — sink đã log hoặc swallow
        }
      }
    }
  }

  Trách nhiệm: điều phối pipeline. Dedupe chống double-fire. Retry/breaker chống
  lỗi transient. Mỗi sink có breaker riêng.

● Phần 4/5: Error handling + Retry/Breaker semantics + Lifecycle

  Nguyên tắc

  1. Không bao giờ throw từ Interceptor layer — nếu onRequest throw, request Dio
  chết. Tất cả exception nuốt bởi InterceptSafe.run().
  2. Sink có quyền throw — Relay chịu trách nhiệm retry/breaker.
  3. Mọi error đều có log — dùng package:logging thay dart:developer để user
  kiểm soát log level + sink.
  4. Idempotency — gửi 1 webhook Discord có thể đã thành công nhưng response
  timeout. Retry phải có cơ chế at-least-once an toàn (Discord accept duplicate
  webhook dedupe tự nó qua wait=true).

  InterceptSafe — wrapper

  class InterceptSafe {
    static void run(String context, void Function() block) {
      try {
        block();
      } catch (e, st) {
        logger.warning('CurlInterceptor[$context] error: $e', stackTrace: st);
      }
    }
  }

  Dùng ở onRequest / onResponse / onError. Không bao giờ rethrow.

  RetryPolicy — exponential backoff + jitter

  class RetryPolicy {
    final int maxRetries;          // default 3
    final Duration initialDelay;   // default 1s
    final double backoffMultiplier;// default 2.0
    final double jitterFraction;   // default 0.2 (±20%)

    Future<T> execute<T>(Future<T> Function() op, {required String
  operationName});
  }

  Hành vi:
  - Cap max delay ở 30s để không treo
  - Jitter ±20% tránh thundering herd khi nhiều request fail đồng thời
  - Lỗi retry được: network exception, HTTP 5xx, HTTP 429 (Discord rate limit)
  - Lỗi không retry: HTTP 4xx khác (lỗi client, không phải lỗi sink)
  - Hết retry → throw RetryExhaustedException, Relay log warning, breaker ghi
  nhận fail

  CircuitBreaker — per-sink, sliding window

  class CircuitBreaker {
    final int failureThreshold;        // default 5
    final Duration resetTimeout;       // default 60s
    CircuitState state;                // closed | open | halfOpen
    int _consecutiveFailures;
    DateTime? _openedAt;

    Future<T> call<T>(Future<T> Function() op);
  }

  Hành vi:
  - closed: gọi bình thường
  - open: skip call, throw CircuitOpenException ngay
  - Sau resetTimeout → halfOpen: cho phép 1 thử nghiệm
    - Thành công → closed, reset counter
    - Fail → open lại, reset timer

  State map Sink.name → CircuitBreaker. Mỗi sink có breaker riêng (Discord fail
  không ảnh hưởng Telegram).

  DedupeCache — TTL + LRU bounded

  class DedupeCache {
    final Duration ttl;            // default 1 min
    final int maxEntries;          // default 10,000 (LRU)
    bool shouldDispatch(String eventId);
    void markDispatched(String eventId);
  }

  - LRU eviction khi đầy (LinkedHashMap insertion-ordered)
  - TTL check lazy trên shouldDispatch (không cần timer nền)
  - eventId = UUID; same UUID trong TTL → drop
  - Lưu ý: dedupe theo UUID, không theo URL. Nếu user gửi cùng URL 2 lần liên
  tiếp (2 request khác nhau, 2 UUID khác nhau) → vẫn gửi cả 2.

  Lifecycle / dispose

  abstract interface class CurlRelay implements Disposable {
    void dispose();   // cancel Timer, clear breakers & cache, await in-flight 
  sink handles (best-effort 5s)
  }

  DioCurlInterceptor.dispose() được gọi khi app teardown. Thứ tự:
  1. Cancel cleanup Timer (nếu có)
  2. relay.dispose() — best-effort drain in-flight handles với timeout 5s
  3. Sink dispose() theo thứ tự ngược lại add (close HTTP client, close Hive
  box)

  Pattern vay từ StreamSubscription.cancel() — dispose idempotent, gọi 2 lần
  không sao.

  Error flow

  Sink.handle(event) throws
     │
     ▼
  Relay._handle bắt → retry (nếu transient)
     │
     ▼
  Retry exhausted / non-retryable
     │
     ▼
  Breaker.recordFailure()
     │
     ▼
  Logger.warning(...)  ← surface visible
     │  (không throw, không break pipeline)
     ▼
  Next sink tiếp tục (mỗi sink độc lập)

  Nếu breaker open:
     │
     ▼
  Sink bị skip, logger.info('sink {name} skipped: circuit open')
     │
     ▼
  Khi resetTimeout hết:
     │
     ▼
  halfOpen → 1 thử nghiệm → success: closed | fail: open
